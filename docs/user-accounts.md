# 일반 사용자 이메일 계정과 Firebase 저장

사용자는 이메일로 회원가입·로그인합니다. 일반 계정에는 관리자 권한이 부여되지 않습니다.

## 저장 동작

- 로그인한 사용자의 찜 추가·해제, 일정 저장·순서 변경·삭제, 최근 본 장소(최대 50개)는 Firestore `userTravel/{uid}`에 직접 저장됩니다.
- 서버 저장 성공을 확인한 후 화면을 갱신합니다. 연결 실패는 표시하며 오프라인 저장은 지원하지 않습니다.
- 로그인·새로고침·탭 복귀 때 자동 조회하고, 화면이 보이는 동안 30초마다 다른 기기의 변경을 확인합니다. 실시간 스트리밍 방식은 아닙니다.
- 브라우저에는 화면 표시용 메모리만 사용하며 여행 자료를 localStorage에 새로 쓰지 않습니다. 비회원은 로그인 후 저장할 수 있습니다.
- 관리자가 등록·수정·공개하는 콘텐츠와 CSV 초안도 기존처럼 Firestore `contentSpots`에 저장합니다.
- 과거 브라우저 자료는 마이페이지의 '이전에 브라우저에 저장했던 자료 이전'에서 한 번 가져올 수 있습니다. 같은 일정 ID는 Firebase 값을 유지합니다. 과거 로컬 원본은 자동 삭제하지 않습니다.

## 인증과 데이터 경계

사용자 쿠키 `kspot_user_session`은 httpOnly, SameSite=Lax, 운영 환경 Secure이며 5일간 유효합니다. 로그인 시 최근 인증 토큰을 검증합니다. Firebase 클라이언트 인증은 메모리 방식이고 관리자 로그인과 분리됩니다.

서버는 검증한 UID로만 자료에 접근합니다. 쓰기 요청의 출처와 UID를 검사하며 Firestore 클라이언트 직접 접근 거부 규칙을 유지합니다. 새 규칙 배포는 필요하지 않습니다.

수정 작업은 Firestore 트랜잭션에서 최신 자료에 적용하므로 서로 다른 장소·일정의 수정이 전체 자료를 덮어쓰지 않습니다. 같은 일정의 동시 편집은 마지막 저장이 반영됩니다. 이미 삭제된 일정의 편집 요청은 거부합니다. 계정 자료는 최대 400KB입니다.

## 운영 설정

Firebase Authentication 이메일/비밀번호 로그인을 활성화합니다. 다른 노트북과 배포 서버에는 같은 Firebase 프로젝트의 환경변수를 설정하고 승인 도메인을 등록합니다. 서버 전용 서비스 계정 개인키는 GitHub에 올리지 않습니다.

실제 브라우저에서 로그인한 계정의 찜 저장과 새로고침 후 유지까지 확인했습니다. 신규 회원가입·재설정 메일 수신·모바일 및 배포 환경 검수는 별도로 필요합니다. 이메일 인증 강제와 회원 탈퇴 화면은 아직 구현하지 않았습니다.

## 주변 관광지도 함께 저장하기

일정 결과 또는 저장 일정 수정 화면에서 각 촬영지의 '주변 5km 관광지 찾아 담기'를 누릅니다. '일정에 추가'를 누르면 로그인 계정의 Firebase에 즉시 저장합니다. `/saved`에서 관광지가 포함된 일정을 다시 열 수 있습니다. 각 일정은 최대 10곳의 관광지를 담을 수 있습니다. 촬영지 삭제 시 연결된 관광지도 함께 제외됩니다.
